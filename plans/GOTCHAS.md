# Gotchas

Curious/non-obvious things hit while building `order-service`. Check before big changes.

## Environment

- **Bash tool cwd resets to repo root between calls** — does not persist like a real shell session. Any command relying on a prior `cd` (e.g. `uv sync`, `uv run`) must either re-`cd` in the *same* command, or use full paths. Bit us once: `uv sync` ran at repo root instead of `order_service/` and **replaced the root `.venv`** (Python 3.8, all Django deps) with an empty Python 3.12 venv, plus stray `.python-version`/`uv.lock` at root. Always `git status` after any `uv`/`venv` operation to confirm only the intended directory changed.
- Root repo venv: Python **3.8.20**, installed via `pip install -r requirements.txt -r requirements_dev.txt` (Poetry-declared but installed with pip here). Interpreter lives at `C:\Users\Isaac Blanco\AppData\Roaming\uv\python\cpython-3.8.20-windows-x86_64-none\python.exe` — use this exact interpreter if the root `.venv` ever needs rebuilding.
- `order_service/` is a **separate uv project** (own `pyproject.toml`, `.venv`, `uv.lock`, Python 3.12 pinned via `.python-version`). Always run `uv` commands from inside `order_service/`, never from repo root.
- No Docker daemon by default in this environment — must ask user to start Docker Desktop. No `docker-compose.yml` exists yet (that's step 7), so local DB verification uses a bare `postgres:11` container (`saleor-dev-db`, host port **15432** — port 5432 was blocked by a Windows permission issue, don't fight it, just use 15432).
- No `psql` on PATH — use `docker exec saleor-dev-db psql -U saleor -d saleor -c "..."`.

## Django / weasyprint

- `saleor.plugins.invoicing.plugin.InvoicingPlugin` fails to import on this Windows machine — `weasyprint` → `cairocffi` can't find `libcairo-2.dll`. This breaks **every** Django system check (`manage.py` anything), because `check_plugins` eagerly imports all `settings.PLUGINS` entries.
  - Workaround used: temporarily comment out the `InvoicingPlugin` line in `saleor/settings.py`, run the Django command, then revert immediately and confirm `git status` shows the file clean again. Don't leave it commented out.
  - Bypassing Django's system checks entirely (e.g. to run migrations) requires going around `manage.py`/`call_command` — use `django.setup()` + `MigrationExecutor` directly, since `django.setup()` alone doesn't trigger plugin imports (only the checks framework does).
  - Even with `InvoicingPlugin` filtered out of a migration target list, Django's migration **graph dependencies** can still transitively require it (e.g. `plugins.0002_auto_20200417_0335` is a data migration that calls `get_plugins_manager()`). Excluding the `plugins` app from `leaf_nodes()` targets is not enough by itself.

## SQLAlchemy mapping onto Django's tables

- **`Enum` columns**: SQLAlchemy's `Enum` type defaults to persisting the Python enum *member name* (`"UNFULFILLED"`), not `.value` (`"unfulfilled"`). Django's `status` column is a plain varchar storing the value. Must use `sqlalchemy.Enum(OrderStatus, values_callable=lambda e: [m.value for m in e], native_enum=False)` or every status column silently breaks Django-side reads.
- **`metadata` is reserved** on SQLAlchemy `DeclarativeBase` (it's `Base.metadata`, the `MetaData` registry). Map the column as `metadata_: Mapped[...] = mapped_column("metadata", ...)` — attribute name different from column name.
- Every NOT-NULL column on `order_order` needs an explicit value on INSERT from this process — Django's Python-side field defaults (e.g. `default=now`, `default=""`) don't apply to a raw SQLAlchemy INSERT. Cross-checked exact schema with `\d order_order` rather than guessing from `models.py` — matched exactly, but easy to miss one (e.g. `language_code` had no server-side default in `_SERVER_DEFAULTS` initially, caused a NOT NULL violation caught by the API test).

## How to test Django-side changes (use this, not a scratchpad script)

- **Use `saleor.tests.settings` (`--ds=saleor.tests.settings`, already wired into `setup.cfg`'s `addopts`), not raw `saleor.settings`.** It sets `PLUGINS = []`, which sidesteps the weasyprint/cairo crash *entirely* — no need for the temporary-comment-out-and-revert dance below. Write a real test file under the relevant app's `tests/` dir and run it with `pytest path/to/test_file.py -v`; don't write one-off `django.setup()` scripts in the scratchpad.
- Real `pytest-django` fixtures already exist for this: `client` (Django test client), `db` (implicit via other fixtures), `order` / `order_with_lines` (has a real `user`), `webhook` (registers an `ORDER_CREATED`-subscribed `Webhook`). Check `conftest.py` / `saleor/tests/fixtures.py` before writing a new one.
- To assert a webhook actually dispatches, you must **opt the plugin back in per-test** — `saleor.tests.settings` sets `PLUGINS = []` globally, so `WebhookPlugin` isn't wired into the manager by default. Pattern used elsewhere in the repo (`saleor/plugins/webhook/tests/test_webhook.py`): take the `settings` fixture and do `settings.PLUGINS = ["saleor.plugins.webhook.plugin.WebhookPlugin"]` inside the test, then `@mock.patch("saleor.plugins.webhook.plugin.trigger_webhooks_for_event.delay")`.
- Root venv is missing pytest/pytest-django by default after a rebuild (see below) — `requirements_dev.txt` as a whole won't install (`codecov==2.1.10` gone from PyPI, `pywatchman` needs a Visual Studio C compiler this machine doesn't have). Install just what's needed to run Django tests: `pytest==6.1.2 pytest-django==4.1.0 pytest-mock==3.3.1 pytest-xdist==1.34.0 pytest-cov==2.10.1 faker==4.14.0 freezegun==0.3.15 vcrpy==4.1.0 pytest-vcr==1.0.2`. `pytest-xdist` specifically is required even for a single test file, since `setup.cfg`'s `addopts` hardcodes `-n auto`.
- `pytest-django` creates and destroys its **own** ephemeral test database per run (`Creating/Destroying test database for alias 'default'...`) — it does not touch the persistent `saleor-dev-db` container's `saleor` database. No manual cleanup needed after these tests, unlike the manual-script/curl checks in steps 1-3.

## Django `django.test.Client` scripts run outside `manage.py` (last resort only)

Only relevant if you must run something outside pytest — prefer the section above.

- Running a standalone script with `django.setup()` + `django.test.Client()` needs `PYTHONPATH` set to the repo root, or `ModuleNotFoundError: No module named 'saleor'` — the script's own directory is on `sys.path`, not the repo.
- `ALLOWED_HOSTS` defaults to `localhost,127.0.0.1` (no `testserver`) — `django.test.Client` requests get `DisallowedHost` unless `ALLOWED_HOSTS` env includes `testserver`. (`pytest-django` handles this for you automatically — another reason to prefer it.)
- If using raw `saleor.settings` instead of `saleor.tests.settings`, the cairo/weasyprint plugin-import crash isn't just a checks-framework thing — `saleor.order.actions.order_created()` calls `get_plugins_manager()` at **request time**, eagerly importing every `settings.PLUGINS` entry including `InvoicingPlugin`. Needs the temporary-comment-out-and-revert workaround from the section above.
- `order_created_event()` (`saleor/order/events.py`) calls `account_events.customer_placed_order_event(user=...)` which does `user.is_anonymous` — **do not pass a raw `None`** for a guest order's user. The real caller (`checkout/complete_checkout.py::_create_order`) always passes `request.user`, which is Django's `AnonymousUser` for guests, never bare `None`. Any new caller of `order_created()` (e.g. the event-intake view) must do `order.user or AnonymousUser()`, since `Order.user` is a nullable FK and legitimately `None` for guest checkouts.

## urllib3 `Retry` silently skips POST by default

- `urllib3.util.retry.Retry(status_forcelist=[...])` only retries **idempotent** HTTP methods by default (`GET/HEAD/PUT/DELETE/OPTIONS/TRACE`) — `POST` is excluded unless you explicitly widen it. On this repo's pinned `urllib3==1.25.10` the param is `method_whitelist` (renamed `allowed_methods` in urllib3 1.26+ — check version before copying this elsewhere). Caught by an actual test: a real local `HTTPServer` returning 503 for `POST /orders/` was hit exactly **once**, not twice, until `method_whitelist=frozenset(["GET", "POST"])` was added to the `Retry(...)` in `saleor/order/order_service_client.py`. Silent failure mode — no exception, no warning, the retry logic just quietly doesn't apply, so a mocked `session.post` test would never have caught this (mocking bypasses the real `urllib3` retry pipeline entirely — this is why `saleor/order/tests/test_order_service_client.py` uses a real stdlib `HTTPServer` instead of `unittest.mock`/`responses`).
- Worth flagging for later: retrying a non-idempotent `POST /orders/` on a 502/503/504 risks a double-created order if the first attempt actually succeeded server-side but the response was lost in transit. Accepted for now per the plan's spec (uniform retry policy across all calls); order-service's `checkout_token` isn't unique-constrained so a retry-induced duplicate wouldn't even collide at the DB level. Revisit if this becomes a real problem — e.g. idempotency key, or excluding POST from the forcelist after all.

## Step 5 broke 17 existing tests — the facade has no default test double

- The moment `resolve_order`/`resolve_order_by_token` (step 5) stopped touching the DB and started calling `order_service_client.get_order`/`get_order_by_token` unconditionally, **every** pre-existing GraphQL order-query test that didn't explicitly mock the client broke — 17 failures in `saleor/graphql/order/tests/test_order.py` alone. Only ran the new facade-specific test file after step 5, not the full existing suite — should have run the full suite immediately, caught this a step late instead. Same issue hit `_create_order` in step 6 (checkout completion): `OrderLine.bulk_create` FKs to `order_order`, so a stub returning a fake id without a real row violates the FK.
- Fix: one **autouse** fixture (`order_service_client_stub` in `saleor/tests/fixtures.py`, loaded globally via root `conftest.py`'s `pytest_plugins`) monkeypatches `saleor.order.order_service_client.{create_order,get_order,get_order_by_token}` for every test, with real Django-ORM reads/writes against the same `order_order` table order-service would use — not id-only mocks. This keeps the entire existing test suite passing unchanged while still exercising the facade's hydration/payload-building code for real. Tests that need to simulate `OrderServiceUnavailable` or a specific canned response still use a plain `mock.patch`/`with` block scoped to that one test — it layers fine on top of the autouse monkeypatch (monkeypatch applies first per test, an inner `mock.patch` overrides for its `with` block and restores back to the stub on exit, then monkeypatch itself restores the real function at teardown).
- Also found (unrelated, environment-specific): this machine already had a stray `ORDER_SERVICE_URL` env var pointing at a real AWS Elastic Beanstalk host (`daytrader-order-service-dev-2...`), which leaked into a test run and produced a `MissingSchema`/network error instead of the expected connection-refused. Not something this project set — if `ORDER_SERVICE_URL` errors look bizarre, `echo $ORDER_SERVICE_URL` first.

## Step 7: docker-compose `local` profile — real issues found bringing it up

- **Root `Dockerfile` bit-rot**: `libssl1.1` isn't installable in current `python:3.8-slim` — the Debian base image floats (no digest pin), and has drifted from buster to bookworm since this Dockerfile was authored; bookworm ships `libssl3`. Fixed by swapping the package name. Same *class* of problem as the `codecov==2.1.10` PyPI-yank issue already logged above — this whole dependency tree is 2020-era and decays a little more every time something actually tries to build it fresh.
- **`requirements_dev.txt`'s `codecov==2.1.10`** (same yanked-package issue as the local venv, see the "How to test Django-side changes" section above) also blocks the Docker image build, since the root `Dockerfile` runs `pip install -r requirements_dev.txt` directly with no way to select a subset. Bumped to `2.1.13`.
- **Celery 5.0.1 CLI syntax**: `celery worker -A saleor.celeryconf:app --loglevel=info -E` (the `Procfile`'s exact `celeryworker` line) fails with `Error: no such option: -A` — Celery 5.0 moved `-A`/`--app` to a **global** option before the subcommand, not after (`celery -A saleor.celeryconf:app worker --loglevel=info -E`). The `Procfile` itself still has the old form and wasn't fixed (nothing exercises it directly), but don't copy it verbatim into anything new.
- **`docker compose stop <service>` vs. a real dead TCP port**: killing a container removes its DNS record from Compose's embedded resolver, so a subsequent request fails via `NewConnectionError: ... No address associated with hostname` (a DNS resolution failure) rather than `ConnectionRefusedError`. This resolves noticeably slower (~8s observed) than the raw TCP-refused case step 4's own `test_connection_refused_raises_quickly` covers (`< 3s` there) — the `(connect, read)` timeout tuple doesn't bound DNS resolution as tightly as an actual TCP handshake attempt. Still bounded/controlled (not a hang), just don't expect the same timing floor between "stopped container" and "port genuinely closed" scenarios when writing assertions against wall-clock time.
- Verified for real: `web` and `order-service` containers actually round-trip through `order_service_client` (called from inside the running `web` container, not mocked) against the real `order-service` container backed by the same Postgres — see `plans/steps/07-docker-compose.md`'s Verification section for the exact commands.

## Deployment target changed after step 6 (before step 7)

- Original steps 7/9 assumed **two** EC2 instances (monolith + order-service), both fully containerized in AWS. Revised design (confirmed with the user before starting step 7): the monolith (`web`+`celeryworker`) runs on the **developer's machine** — natively or via a `monolith` Compose profile — pointed at AWS-hosted RDS (Postgres) + SQS (Celery broker, replaces Redis in the cloud path) + a single order-service EC2 instance. Only order-service actually gets deployed.
- Consequence: RDS must be `publicly_accessible = true` (the monolith isn't in the VPC anymore) with its security group locked to `var.my_ip/32` — a deliberate, documented lab-only tradeoff, not something to carry into a real deployment.
- `docker-compose.yml` (step 7) now uses Compose **profiles** (`local` / `monolith` / `order-service`) instead of one fixed 5-service stack — `docker compose --profile local up` for pure local dev, `--profile monolith`/`--profile order-service` with `ENV_FILE=.env.cloud` for the AWS-pointed runs.
- Known unsolved gap (documented in step 7, not fixed): in `order-service`-only mode there's no stable `DJANGO_EVENTS_URL` to hand order-service, since the monolith is on a developer laptop with no fixed address — needs a tunnel (ngrok etc.) or acceptance that the webhook round-trip is best-effort in that mode.
- See `plans/00-master-plan.md`'s "Revised target deployment" section for the full rationale; `plans/steps/07-docker-compose.md` and `09-terraform-aws.md` were rewritten accordingly, `08-golden-fixture-tests.md` lightly adjusted.

## order_service's default DB URL doesn't match the Docker port workaround

- `app/config.py`'s `async_database_url` default hardcodes port **5432**, but (per the Environment section above) local Postgres is on **15432**. Running `uv run pytest` in `order_service/` with no env override → every DB-touching test fails with `ConnectionRefusedError` (not an auth/schema error, so easy to misdiagnose as something else). Fix: `ASYNC_DATABASE_URL="postgresql+asyncpg://saleor:saleor@localhost:15432/saleor" uv run pytest -q`.

## pytest-asyncio + async SQLAlchemy

- Default per-test event loop (pytest-asyncio's function-scoped loop) conflicts with a **module-level** `create_async_engine()` — the asyncpg connection pool gets bound to whichever loop created it first, then errors with `InterfaceError: cannot perform operation: another operation is in progress` on later tests running in a new loop. Fix: pin `asyncio_default_fixture_loop_scope = "session"` and `asyncio_default_test_loop_scope = "session"` in `[tool.pytest.ini_options]` so the whole test session shares one loop (mirrors the single-loop reality of a running uvicorn app anyway).
